# BIOCAD — вопросы к собеседованию по задачам WB-01…WB-18

Учебные ответы; подтверждайте каждый кодом, тестами и PR. Сверка с кодом v1.4.2,
статусы реализовано/не реализовано и демо-сценарий — в [PLAYBOOK](PLAYBOOK.md).

## WB-01 · Репозиторий, Docker Compose, каркас CI

1. **Почему monorepo, а не несколько репозиториев?**

   Совместная история API/UI, один набор сквозных тестов и простой локальный старт. Python-схемы и TypeScript-типы находятся в своих сервисах; общего генерируемого пакета типов сейчас нет. Отдельные Dockerfile дают независимые контейнеры; текущий pipeline проверяет и публикует весь комплект, selective builds не реализованы.

2. **Чем readiness отличается от liveness?**

   Liveness подтверждает, что процесс жив; readiness — что сервис готов принимать запросы с нужными зависимостями. Не следует перезапускать сервис лишь из-за временного падения необязательного AI.

3. **Как обеспечить воспроизводимость?**

   Фиксируем зависимости и версии образов, делаем миграции и идемпотентный seed, храним `.env.example` без секретов и проверяем `docker compose up -d` в чистом окружении.

4. **Зачем smoke E2E ещё до бизнес-функций?**

   Он проверяет цепочку веб → API → инфраструктура, поэтому конфигурационный дефект ловится до начала разработки фич. Честно отмечаем, если это пока лишь проверка стартовой страницы.

## WB-02 · Booking API, PostgreSQL, конкурентность

1. **Почему одного SELECT перед INSERT недостаточно?**

   Два потока могут одновременно увидеть свободное место; проверка вне ограничения БД допускает TOCTOU race. Exclusion constraint в PostgreSQL атомарно отклоняет пересекающиеся интервалы.

2. **Почему `[start, end)`, а не закрытый интервал?**

   Полуоткрытые границы позволяют брони 09:00–12:00 и 12:00–13:00 существовать вплотную. `tstzrange(start_at,end_at,'[)')` и оператор `&&` описывают пересечение.

3. **Что означает идемпотентность подтверждения?**

   Повтор того же запроса с тем же ключом получает ту же бронь; тот же ключ и другой payload — ошибка. Ключ вместе с хешем тела и результатом хранится в БД, а не только в памяти процесса.

4. **Как доказать отсутствие двойной брони?**

   Запускаем параллельные запросы в реальный PostgreSQL и ожидаем ровно один успех, остальные конфликт. Затем временно отключаем constraint в изолированном тесте, демонстрируем красный тест и возвращаем защиту.

## WB-03 · React + SVG карта

1. **Почему SVG, а не Canvas?**

   Для десятков мест SVG проще сделать кликабельным, масштабируемым, доступным с клавиатуры и тестируемым через DOM. Canvas оправдан при десятках тысяч примитивов, но сложнее для a11y.

2. **Как разнести координаты плана и бизнес-статусы?**

   Схема хранит нормализованные координаты и геометрию, а API отдаёт статусы по выбранному периоду; React объединяет их по `space_id`. Замена этажа не требует ручной перерисовки статусов.

3. **Как избежать ложной «свободности» при устаревшем UI?**

   На карте показываем время обновления, вручную обновляем и используем polling; перед сохранением Booking Service повторно проверяет правила. UI — только предварительный индикатор.

4. **Что проверить Playwright?**

   Выбор этажа/времени, zoom/fit, Tab+Enter на desk, видимую легенду, пустую выдачу и состояние ошибки API; тесты используют стабильные `data-testid`, а не координаты мыши.

## WB-04 · Сотрудники, аватарки, постоянные места

1. **Почему аватарка не доказывает присутствие человека?**

   Система знает назначение рабочего места или бронирование, но не проверяет фактический вход в офис. Поэтому подпись «закреплено за» или «забронировано сотрудником» обязательна; «сейчас сидит» недопустимо без отдельного источника присутствия.

2. **Как меняется аватар при выборе календаря?**

   Frontend запрашивает `GET /api/v1/spaces?floor_id&from&to` (алиас `/api/v1/floors/{id}/occupancy`), backend возвращает пересечения броней и назначения. Из ответа строятся avatar overlays, клик открывает ФИО, должность и точные интервалы МСК.

3. **Что если на одном FreeDesk два человека в разные часы выбранного окна?**

   Не показываем случайную одну аватарку: используем стек аватарок с меткой `2` и список интервалов в панели. Для конкретного слота 12:00–14:00 между бронями место может быть свободно.

4. **Какие риски приватности у карты сотрудников?**

   Нужны вход, минимизация данных и согласие на LLM. В демо — только вымышленные профили/иллюстрации; backend не имеет полноценной ролевой модели доступа по офисам/этажам, это требование будущей корпоративной интеграции, а не готовая возможность. API ответам выставлен no-store; приватность не обеспечивается одной лишь запретительной подсказкой модели.

## WB-05 · Форма, мои брони, отмена

1. **Почему подтверждение — отдельный шаг?**

   Выбор карточки — исследование доступности, а создание записи — значимое действие. Чёткое финальное подтверждение снижает случайные брони и выполняет исходное требование.

2. **Чем 201, 200, 409 и 422 отличаются в API?**

   201 — новая бронь, 200 — тот же результат повторной идемпотентной операции, 409 — конфликт ресурса или ключа, 422 — некорректные входные параметры.

3. **Как запретить отмену чужой брони?**

   Сервер берёт пользователя из доверенной сессии, сверяет `booking.employee_id` и не доверяет идентификатору из React. Отмена идемпотентна и немедленно обновляет карту.

4. **Что делать при потере ответа после создания?**

   Клиент повторяет запрос с прежним idempotency key, а не генерирует новый. Сервер вернёт существующую запись и не создаст дубль.

## WB-06 · Реальная LLM, MCP, RabbitMQ RPC

1. **Что даёт MCP сверх обычного prompt?**

   Он стандартизирует доступ модели к инструментам получения актуальных данных: списку мест, сотрудникам, занятости. Текст LLM не является источником истины, а аргументы и ответы tools валидируются.

2. **Почему AI не создаёт бронь сам?**

   Модель может галлюцинировать ID и время. После явного подтверждения отдельная команда идёт в Booking Service, где выполняются авторизация, idempotency и exclusion constraint.

3. **Когда выбирать RabbitMQ RPC, а когда событие?**

   RPC нужен для актуального ответа на запрос AI с correlation_id и deadline; событие — для независимого уведомления после коммита. Ошибка потребителя не должна откатывать созданную бронь.

4. **Что делать с prompt injection?**

   Сообщения пользователя, названия комнат и tool responses считаем недоверенными. У модели ограничен набор инструментов, а все write-операции проходят серверные разрешения и подтверждение.

## WB-07 · Notification Worker, RabbitMQ, Mailpit

1. **Почему нужен transactional outbox?**

   Факт бронирования и запись события коммитятся в одной транзакции, поэтому сбой брокера не теряет событие. Publisher позднее доставляет его в RabbitMQ.

2. **Что означает at-least-once delivery?**

   Сообщение может прийти повторно; Worker фиксирует inbox до ACK и дедуплицирует завершённые доставки по `event_id`. SMTP acceptance и commit inbox не атомарны: при падении между ними возможно повторное письмо. Stable Message-ID не доказывает exactly-once SMTP.

3. **Зачем Mailpit, если есть SMTP?**

   Он безопасно перехватывает тестовые письма, показывает HTML и text части, предоставляет API для integration-теста и не отправляет письмо реальному человеку.

4. **Как защитить шаблоны писем?**

   Экранировать пользовательские поля, проверять корректную timezone МСК, добавлять plain-text fallback и не выводить PII в общедоступных логах.

## WB-08 · Allure, unit/integration/E2E, доказательство дефекта

1. **Чем unit отличается от integration и E2E?**

   Unit проверяет бизнес-правило в изоляции; integration проверяет реальную БД/очередь; E2E проверяет пользовательскую цепочку в браузере. Все уровни нужны, но отвечают на разные вопросы.

2. **Зачем сознательно ломать защиту в тесте?**

   Это демонстрация чувствительности теста: с отключённым constraint конкурентный тест должен упасть, после возврата — пройти. Дефектный код не вливается и тест запускается только в одноразовой БД.

3. **Как бороться с flaky E2E?**

   Фиксированный seed, ожидания по состояниям/API вместо угаданных sleep, отдельная среда и изоляция пользователей. В проекте сохраняются screenshots и отчёт; authenticated Playwright traces отключены, чтобы не экспортировать cookies/CSRF.

4. **Что публиковать в Allure?**

   Run type smoke/regression, SHA, working_tree, окружение, suite, шаги, ошибки, screenshots и безопасные логи. У smoke/regression сейчас один набор тестов с разными metadata; Vitest учитывается отдельно от raw Allure. Actions artifacts имеют retention, основные доказательства сохраняются также в release assets. Authenticated traces не публикуются.

## WB-09 · GitHub Actions → Docker Hub → staging → production

1. **Почему image digest важнее `latest`?**

   `latest` изменяем; digest идентифицирует точный набор байтов. После staging не пересобираем Docker image, а продвигаем проверенный digest к версии и latest.

2. **Зачем staging и полная регрессия на нём?**

   После merge полный набор выполняется на сервере в новом disposable Compose-проекте с реальными сервисами и вымышленными данными. Затем persistent staging обновляется точными digest и проходит smoke. Fault injection не выполняется на его постоянной БД. Main повторяет полный gate и продвигает тот же проверенный manifest в production.

3. **Как защитить deploy webhook?**

   Проверять HMAC/signature, timestamp, replay, allowlist действий и использовать минимальные права на сервере. В проекте webhook не используется: выбран GitHub Actions deploy job по SSH с ключом `restrict,command=...` и dispatcher, принимающим только allowlist JSON-операций ([bootstrap_server.py](../../scripts/bootstrap_server.py), [deploy_server.py](../../scripts/deploy_server.py)).

4. **Как откатить ошибочный релиз?**

   Хранить предыдущие image digests, конфигурацию и backup БД; rollback возвращает контейнеры, но миграции требуют отдельной стратегии совместимости. Автоматически откатывать схему без оценки рисков нельзя.

## WB-10 · README, C1/C2, ADR, AI-LOG

1. **Что показывают C1 и C2?**

   C1 — пользователи и внешние системы; C2 — контейнеры, обязанности, способы связи и владение данными. Это уровни C4-модели, а не произвольные диаграммы классов.

2. **Зачем ADR?**

   Кратко сохраняет проблему, решение, альтернативы и последствия для важных компромиссов. Например, почему выбран exclusion constraint и почему RabbitMQ + outbox.

3. **Что писать в AI-LOG?**

   Какие задачи реально выполнял разработчик и агент, 2–3 проверенных решения с PR/тестами и разногласия. Не выдумывать использованные модели, затраты и проходы CI.

4. **Как собеседующему воспроизвести запуск?**

   README содержит команды, секреты только в примере env names, seed, тестовые логины, пути Allure, миграции и restore; без доступа к личной машине разработчика.

## WB-11 · Исправление ошибки конкурентности

1. **Как отделить баг от фичи в версии?**

   Изменение только поведения существующей функции — `fix` и PATCH; новая пользовательская возможность — `feat` и MINOR. Если в релизе есть фича, он получает новый MINOR.

2. **Как воспроизвести race condition?**

   Синхронизированные барьером клиенты шлют конкурирующие запросы в один интервал на тот же ресурс. Логи correlation_id и SQLSTATE помогают установить место отказа.

3. **Почему нельзя закрывать race только блокировкой React?**

   Клиенты могут работать в разных вкладках/устройствах, запросы приходят одновременно и обходят UI. Гарантию обеспечивает сервер и БД.

4. **Как подтвердить исправление?**

   Сохраняем исходный сбой, добавляем проверку конкретного дефекта и запускаем её с исправлением; после merge — полная серверная регрессия в disposable среде и staging smoke. WB-08 RED без constraint доказывает чувствительность oracle отдельно от WB-11: в реальном deadlock-сбое constraint оставался включён, пересечений не было, но возникал HTTP 500. Исправление прошло focused/full проверки и выпущено как PATCH v1.4.1.

## WB-12 · OpenRouter LLM failover

1. **При каких ошибках переходить на резервную модель?**

   При предусмотренных 429/5xx/timeout/ошибках конкретной модели с ограниченным числом попыток; 401/402/доступность ключа могут требовать отдельной обработки и не гарантируют обход через free model.

2. **Почему нельзя выбирать случайную `:free` модель?**

   Нужны совместимые tool calling, структурированные ответы, лимиты и условия обработки данных. Прогнать contract tests и держать ограниченный allowlist моделей.

3. **Что показывает React при fallback?**

   Текущий статус primary/fallback/unavailable, нейтральное предупреждение «AI может ошибаться» и возможность продолжить через форму без AI.

4. **Почему не нужно доверять ответу резервной модели больше?**

   Любая модель допускает ошибки; валидатор схемы, MCP живые данные и Booking Service обеспечивают безопасность независимо от стоимости модели.

## WB-13 · Комфортный поиск по условиям

1. **Как разделять жёсткие ограничения и предпочтения?**

   Этаж ≤2 и минимальная дистанция до HVAC — hard filters, они должны соблюдаться. «Желательно у окна» — soft score, может влиять на сортировку, но не отменяет проверку доступности.

2. **Что делать с неизвестным уровнем шума?**

   Показать «данных недостаточно», не принимать unknown за тихо и не давать категорическую гарантию. Источник параметра (демо, отзыв, сенсор) хранить отдельно.

3. **Что делает LLM, а что алгоритм?**

   LLM разбирает человеческий запрос в валидируемые поля и формулирует объяснение; backend выполняет жёсткие фильтры и детерминированное ранжирование.

4. **Как проверить качество рекомендаций?**

   Golden test queries, unit-tests ranking и hard constraints, интеграция MCP+занятость, Playwright для подсветки; объяснение должно ссылаться на реальные атрибуты, а не выдуманные.

## WB-14 · Добровольный квиз комфорта

1. **Почему квиз нельзя делать обязательным?**

   Быстрое бронирование — базовый сценарий; квиз должен улучшать опыт, а не блокировать его. Нужны «Пропустить», частичные ответы, редактирование и удаление.

2. **Что хранить в профиле?**

   Практические предпочтения, такие как окно/шум/этаж, а не медицинские сведения или психологические характеристики. Собственные ответы пользователь видит и может удалить.

3. **Как избежать ложной персонализации?**

   Результат вычисляется из явно указанных ответов и проверенных атрибутов мест; unknown не заменяется уверенностью. Объяснения показывают причины рекомендаций.

4. **Какие тесты нужны?**

   Unit scoring и валидация, integration save/load/delete preferences, E2E квиз → подходящее свободное место → подтверждение; smoke для пропуска.

## WB-15 · Отзыв, повторная бронь и альтернативы

1. **Когда запросить отзыв?**

   Только после завершённой confirmed-брони, не после отменённой; не более одного запроса на бронь, с возможностью отказаться.

2. **Почему положительный отзыв не создаёт автоматическую бронь?**

   Предпочтение места — не согласие на новую дату/интервал. Нужно снова проверить доступность, показать условия и явно подтвердить.

3. **Как интерпретировать жалобы на жару/шум?**

   Как субъективный опыт конкретного сотрудника; одно сообщение не превращается в инженерное измерение для всех. Можно понизить личный приоритет места и предложить альтернативу.

4. **Какая проверка приватности обязательна?**

   Отзыв только о своей завершённой брони, индивидуальные предпочтения не показываются коллегам и не уходят в LLM без минимизации и правового основания.

## WB-16 · Календарная карта аватарок и несколько броней

1. **Как определить набор людей на месте для выбранного интервала?**

   Для каждой подтверждённой брони используем пересечение `booking.start < selected_end AND selected_start < booking.end`; постоянное назначение рассчитываем по периоду действия отдельно.

2. **Как показать две брони в одном выбранном окне?**

   Стек из двух мини-аватарок с числом и таймлайн, например 10:00–12:00 Иванов, 14:00–16:00 Соколова. На карте не приписываем владельца всего дня одному человеку.

3. **Как React предотвращает появление устаревших аватарок?**

   AbortController/идентификатор запроса, ключ cache `floor+from+to`, skeleton и атомарная смена snapshot. Старый ответ после переключения календаря не перерисовывает новый период.

4. **Как сохраняется возможность бронирования промежутка?**

   Если пользователь выбирает 12:00–14:00, межслотовое окно считается свободным. При выборе 09:00–17:00 место частично занято и целиком забронировать его нельзя.

## WB-17 · Task notes, релизная история и SemVer

1. **Почему note на каждую задачу не равен GitHub Release?**

   Завершение PR формирует запись об изменении, а новая версия публикуется лишь после полного regression и staging. Несколько PR могут войти в один release.

2. **Откуда берётся история релизов в интерфейсе?**

   План: из версионированного `releases.json`, собираемого CI при release-публикации, либо read-only endpoint. Не смешивать опубликованные версии с черновиками задач. Статус v1.4.2: in-product страницы нет; опубликованные версии — GitHub Releases и `docs/releases/`.

3. **Как работает SemVer для тестового задания?**

   `1.MINOR.PATCH`: новая функция повышает MINOR с PATCH=0, исправление — PATCH; major остаётся 1 по договорённости, несовместимость документируется отдельно.

4. **Что делать, если релизный pipeline завершился неуспешно?**

   Не показывать его в публичной истории как опубликованный. Сохранить candidate evidence, красный Allure и новую fix-задачу; историю обновлять после prod smoke.

## WB-18 · Подготовка к собеседованию, evidence

1. **Как объяснить решение, которого вы лично не писали?**

   Показать критерии выбора, альтернативы, где код, тест и компромисс; AI-LOG честно отделяет помощь агента от личной проверки.

2. **Что назвать главным архитектурным инвариантом?**

   Единственный владелец записи — Booking Service и PostgreSQL. Клиент, LLM, очередь и email не могут нарушить эксклюзивность брони.

3. **Какие сценарии показать live?**

   Два параллельных пользователя на один слот; смежные интервалы; смена времени и аватарок; AI отказ; повтор подтверждения; письмо в локальном Mailpit; Allure и GitHub Releases (in-product Release History не реализована). Пошаговый сценарий — [PLAYBOOK](PLAYBOOK.md).

4. **Как отвечать на вопросы о незавершённых P1/P2?**

   Не выдумывать функциональность: показать статус, код/макет, критерии и очередь задач; объяснить почему при трёх днях приоритет отдан корректности P0.
